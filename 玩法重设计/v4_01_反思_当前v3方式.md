# v4 反思 —— 当前 v3 方式的根本问题

> 日期：2026-08-13 ｜ 对象：`原型\demo-v3\`（上帝视角 MVP）与 `玩法重设计\00_玩法重设计总纲_v3_上帝视角.md`
> 结论：v3 把"操作"从微观提到了宏观（方向对），但**底层的数值模型仍是"点击挂机"的加法引擎**——只是把"放节点"的点击交给了自动体。本文件诊断病灶，为 v4 改法（`v4_02`）提供依据。

---

## 1. 五个病灶

### 病灶 A：节点仍在"堆量"，没有"统合"

`game.js` 的自动体 `decideBuild()` 每 1.2 秒挑一个节点建（森林/篝火/农田），成长本质是：

```
总功率 = Σ(同类节点 × 单节点功率)
```

多一个篝火 = +100kW，多一个森林 = 多养一个篝火。这是**加法**——玩家（或自动体）靠"数量"变强，没有"整合"的概念。用户要的是"所有节点统合在一起"，即**节点之间是功能串联的关系（采集→加工→消费→收集），而不是并列的同类堆叠**。

### 病灶 B：能量 = "消耗"，不是"利用"

`settle()` 里能源节点的结算只有一句：

```js
if (state.stock[k] >= need) { state.stock[k] -= need; n.power = t.power * mult; }
```

燃料被"烧掉"→ 直接变成瓦特。这条链缺了**目的**：木头为什么被烧？是为了**烹饪生食→熟食→喂饱定居点→产出劳动力与科技**。能量在 v3 里是"被消耗的燃料"，而不是"被利用来做一件有产出的事的中间投入"。EROI 因此退化成"发电效率"，而不是"一次利用是否净赚"。

### 病灶 C：乘数散落，没有"窗口"与"小乘数"

v3 的乘数散在七八个地方：`traits`、`creeds`、`pillars`、`techNodeMult`、`regionBonus`、`cultureBonus`，各自独立乘进 `totalPower()` / `researchRate()`。玩家**看不到"我的产出为什么是这个数"**。用户要的是：一个**窗口**（经济总览），里面有一个**表达乘数的小乘数**（可分解展示：基础 × 规模 × 技术 × 国策）。

### 病灶 D：没有真实供需，定居点不是"消费端"

v3 的资源是**全局池**（`stock`），源直接喂能源。没有"定居点作为消费端"、没有"供<需→劳动力/科技下降（饥荒）"的闭环。没有消费端，就没有"经济体量"与"运营"可言。

### 病灶 E：缺"收集节点"，劳动力/科技是散数字

劳动力、科技点、文化是三个散落的 `state` 字段，没有一个**收集节点**把它们统合起来、并承载"窗口 + 乘数"。用户明确点名"再有一个收集节点进行收集"。

### 病灶 F：无规模效应，鼓励"摊大饼"而非"集中整合"

建 10 个小森林和建 1 个"大森林"（如果有）没有区别，甚至摊大饼更省心。没有"整合/规模带来效率"的奖励，这与《维多利亚3》的规模经济背道而驰。

---

## 2. 根因一句话

> **v3 的交互层是"上帝视角"，但数值层还是"点击挂机"**：把"放节点"的点击替换成自动体，没有替换掉"加法堆量 + 燃料消耗"的内核。

交互层的升维（国策/权重/探索/裁决）是对的，应当保留；要动的是**数值模型的骨架**：从"并列加法"改为"功能管线 + 乘数统合 + 能量利用"。

---

## 3. 什么该留、什么该改

| 维度 | 保留（对） | 要改（病灶） |
|---|---|---|
| 交互视角 | 上帝视角、宏观动词（国策/权重/探索/裁决） | — |
| 节点模型 | 节点这个载体 | 从"并列堆量"改为"功能管线"（采集/加工/定居/收集） |
| 能量语义 | — | 从"消耗"改为"利用"（能量是加工的目的性投入） |
| 乘数体系 | — | 从"散落"改为"统一窗口 + 可分解乘数" |
| 供需 | — | 引入"定居点消费端 + 缺口反馈" |
| 规模 | — | 引入"整合系数 + 规模经济" |
| 收集 | — | 引入"收集节点"作为窗口载体 |
